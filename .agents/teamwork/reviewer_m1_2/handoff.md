## 2. Logic Chain

1. **Idempotency & Safe Migration**:
   - The database migration script and the runtime bootstrap method use purely additive, idempotent SQL statements (`IF NOT EXISTS` clauses on tables, columns, and indexes).
   - Double-quoting `"user"` prevents PostgreSQL syntax conflicts with the reserved keyword `user`. Quoting `"sourceInstitution"` and `"createdAt"` prevents PostgreSQL from lowercasing camelCase identifiers, maintaining 1:1 mapping with Drizzle ORM column declarations.
   - Dual-provisioning (`CREATE TABLE IF NOT EXISTS` + `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`) guarantees that both fresh database installations and existing partially migrated schemas converge to the exact same table structure without errors.

2. **Bootstrap Resilience**:
   - `TutoriaService.onModuleInit()` ensures tables on application startup.
   - The try/catch block around DDL execution logs warnings instead of crashing the process. This guarantees that in environments with read-only replicas or transient network interruptions during boot, NestJS successfully starts and serves unaffected endpoints.
   - The in-memory boolean flag `hasEnsuredTimelineTable` guarantees that DDL is not executed repeatedly during high-volume HTTP requests.

3. **Production Alignment & Build Hygiene**:
   - Registration of both TS (`tsx`) and production (`node dist/...`) migration commands supports local development as well as containerized production deployment.
   - Build output cleanly emits `dist/db/migrate-tutoria-multitutor.js` and `.d.ts` without TypeScript diagnostics or bundling issues.

4. **Integrity Verification**:
   - Tests do not use hardcoded facades, bypasses, or fake pass assertions.
   - Mock DB objects appropriately simulate database driver query execution and error rejection.

## 3. Caveats

- **Database Connection for CLI Script**: Running `npm run db:migrate-tutoria-multitutor` directly against a real PostgreSQL instance requires a running database accessible via `DATABASE_URL`. In environments without PostgreSQL active, execution will terminate with `process.exit(1)` as designed.
- **`tsx` Monorepo Hoisting**: The script `"db:migrate-tutoria-multitutor": "tsx ..."` resolves `tsx` from the monorepo root `node_modules/.bin`. If `apps/backend` were built or packaged in isolation without monorepo hoisting, adding `tsx` to backend `devDependencies` would provide extra portability (detailed in Minor finding below).

## Findings

### [Minor] Finding 1: Explicit `tsx` Dependency in Backend Workspace
- **What**: Script `"db:migrate-tutoria-multitutor": "tsx src/db/migrate-tutoria-multitutor.ts"` relies on `tsx` hoisted from the root monorepo `node_modules`.
- **Where**: `apps/backend/package.json`, lines 21 & devDependencies.
- **Why**: Currently works seamlessly because npm workspace hoists `tsx` v4.22.3 to the root `node_modules/.bin`. If backend is ever extracted or packaged independently into a standalone Dockerfile without root devDependencies, `tsx` would not be resolved.
- **Suggestion**: Consider adding `"tsx": "^4.22.3"` directly into `apps/backend/devDependencies` during Milestone 5 (Hardening) for standalone packaging isolation.

### [Minor] Finding 2: Unit Test Error Injection Scope
- **What**: In `tutoria.service.spec.ts`, `mockDb.execute.mockRejectedValueOnce(new Error('Connection offline'))` only rejects the first `execute` call (handled by `ensureKanbanTable()`).
- **Where**: `apps/backend/src/tutoria/tutoria.service.spec.ts`, lines 88–91.
- **Why**: `ensureTimelineTable()` first invokes `await this.ensureKanbanTable()`. Since `mockRejectedValueOnce` only rejects the first call, `ensureKanbanTable` catches the error, but the subsequent DDL inside `ensureTimelineTable` resolves successfully.
- **Suggestion**: In Milestone 2 or 5, consider using `mockRejectedValue(new Error('Connection offline'))` or running tests against both methods individually to explicitly trigger `ensureTimelineTable`'s own catch block warning.

## Challenges

### [Low] Challenge 1: Out-of-Order Standalone Script Execution
- **Assumption challenged**: Running `npm run db:migrate-tutoria-multitutor` assumes `tutoria_atendimentos_kanban` already exists.
- **Attack scenario**: If a brand-new database is provisioned and a developer executes `npm run db:migrate-tutoria-multitutor` *before* running `npm run db:migrate-tutoria`, the foreign key `REFERENCES tutoria_atendimentos_kanban(id)` will fail.
- **Blast radius**: CLI migration fails with exit code 1; no corrupt state created.
- **Mitigation**: Runtime bootstrap in `TutoriaService.ensureTimelineTable()` explicitly calls `await this.ensureKanbanTable()` before creating the timeline table, eliminating this risk for the running application. For manual migrations, documentation in README/deployment guides dictates running migrations sequentially.

### [Low] Challenge 2: Concurrent Multi-Pod Startup Race Condition
- **Assumption challenged**: Multiple NestJS pods booting simultaneously execute `ensureTimelineTable()`.
- **Attack scenario**: Concurrent execution of `CREATE INDEX IF NOT EXISTS` in PostgreSQL can occasionally trigger catalog lock contention or duplicate key notices in older PG engines.
- **Blast radius**: Negligible. Both `ensureKanbanTable()` and `ensureTimelineTable()` are wrapped in non-fatal `try / catch` blocks with warnings logged, ensuring application startup never fails due to DDL concurrency.
